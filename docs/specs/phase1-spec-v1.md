## Problem Statement

Monitor ERP 的实施项目目前缺乏统一的协作平台：客户资料、蓝图、实施阶段、会议纪要、问题清单分散管理，内部员工（实施/开发/售后）与外部客户（项目经理/Key User/普通用户）各自使用割裂的工具；知识库文档无法复用，客服问答没有智能化支撑，客户操作手册需要人工编写。

## Solution

构建一个**多租户 SaaS 平台**，让 Monitor ERP 内部员工与外部客户在**一个平台上**协作完成实施项目管理：客户资料、蓝图（版本化）、实施阶段/风险、会议纪要、问题清单，加上内部 + 客户两级 RAG 知识库、内部客服 AI Agent 和客户操作手册自动生成。数据边界 = 项目；数据隔离是最高优先级红线（数据库层 RLS + RAG 层每客户 Index + 后端注入检索范围）。

## User Stories

### 身份与认证

1. 作为内部用户，我想用邮箱+密码登录平台，以便访问内部功能
2. 作为客户用户，我想用邮箱+密码登录平台，以便访问被授权项目的数据
3. 作为超级管理员，我想创建内部用户账号，以便分配实施/开发/售后等角色
4. 作为超级管理员或内部用户，我想在项目内邀请客户用户并生成一次性邀请链接，以便客户用户首次设置密码加入平台（链接由邀请者复制分发，系统不发送邮件）
5. 作为客户项目经理，我想在自己项目内邀请/停用普通用户（Key User/普通用户），以便管理项目成员
6. 作为客户用户，我想通过邀请链接首次设置密码，以便激活账号
7. 作为用户，我想退出登录，以便保护账号安全
8. 作为用户，我想在 Token 过期后自动刷新会话，以便不中断工作
9. 作为用户，我想在忘记密码时重置密码，以便恢复访问

### 客户资料

10. 作为内部用户，我想创建客户（名称、行业、地域等基础资料），以便建立客户档案
11. 作为内部用户，我想编辑客户资料，以便保持信息最新
12. 作为内部用户，我想查看/搜索全部客户列表，以便快速定位客户
13. 作为客户用户，我想查看所属客户的资料（只读），以便了解组织信息

### 项目与成员

14. 作为超级管理员，我想创建项目并归属到客户，以便客户可以有多个实施项目
15. 作为内部用户，我想创建项目并归属到客户、维护项目基本信息，以便管理实施
16. 作为客户用户，我想查看我被授权的项目，以便参与项目实施
17. 作为客户用户，我想只能看到我有成员身份的项目（不跨项目），以便数据隔离

### 蓝图

18. 作为内部用户（实施），我想创建/上传蓝图（draw.io 流程图 + 结构化文档），以便记录实施设计
19. 作为内部用户，我想编辑蓝图并生成新版本，以便蓝图带版本控制、可追溯
20. 作为内部用户，我想查看蓝图版本历史，以便对比演进
21. 作为客户用户，我想查看本项目的蓝图（只读），以便了解实施内容
22. 作为用户，我想在问题条目中关联蓝图，以便追溯问题上下文

### 实施阶段与风险

23. 作为内部用户，我想基于标准阶段模板创建实施阶段，以便快速搭建项目计划
24. 作为内部用户，我想在项目内增删/调整阶段，以便适配实际实施节奏
25. 作为内部用户，我想流转阶段状态（未开始/进行中/已完成/已暂停），以便跟踪进度
26. 作为客户用户，我想查看项目实施阶段及状态，以便了解项目进度
27. 作为内部用户，我想创建风险点（描述、等级高/中/低、状态、负责人），以便管理项目风险
28. 作为内部用户，我想把风险关联到具体阶段，以便定位风险影响范围
29. 作为内部用户，我想更新风险状态与负责人，以便风险闭环
30. 作为客户用户，我想查看项目风险点，以便了解潜在影响

### 会议纪要

31. 作为内部用户，我想创建会议纪要（主题、日期、参会人、富文本正文），以便记录会议成果
32. 作为内部用户，我想上传/管理纪要附件，以便保存会议材料
33. 作为内部用户，我想编辑/删除会议纪要，以便修正记录
34. 作为客户用户，我想查看会议纪要，以便跟进会议决议
35. 作为客户用户，我想下载/预览纪要附件，以便获取会议材料

### 问题清单

36. 作为客户用户（普通用户/Key User/项目经理），我想提交问题（标题、描述、类型、分类：功能/数据/使用/技术/优化、优先级），以便反馈实施中的问题
37. 作为内部用户，我想查看并处理项目问题（指派内部负责人、状态流转：新建→处理中→已解决→已关闭），以便推动问题解决

39. 作为 Key User 或项目经理，我想评论问题，以便补充信息、讨论解决方案
40. 作为普通用户，我想查看项目问题列表，以便跟踪自己提交的问题状态（评论权限受限，遵守权限矩阵）
41. 作为用户，我想按分类/优先级/状态/提交人筛选和搜索问题，以便快速定位
42. 作为用户，我想在问题中关联蓝图/功能/文档，以便上下文可追溯
43. 作为内部用户，我想看到所有客户的问题（内部全权限），以便统一支持

### 内部知识库

44. 作为内部用户，我想用 Markdown 编辑器在线创建/编辑知识库文档，以便沉淀操作手册/FAQ/最佳实践
45. 作为内部用户，我想上传文件类文档（Word/Excel/PDF 等），以便纳入知识库
46. 作为内部用户，我想给文档分类（操作手册/FAQ/最佳实践），以便组织知识
47. 作为内部用户，我想控制文档生命周期（草稿→已发布→已归档）并查看版本历史，以便发布管理
48. 作为内部用户，我想编辑已发布文档生成新草稿版本（重新发布才生效），以便更新知识而不破坏线上内容
49. 作为内部用户，我想归档文档，以便下架过期内容（归档自动从 RAG 删除）
50. 作为内部用户，我想查看文档的 RAG 同步状态，以便确认知识已可检索（增强项，见 Implementation Decisions）

### Online help 导入

51. 作为内部用户，我想通过导入 API / 定时同步接入外部项目的 Online help 文档（只读、增量），以便内部知识库覆盖产品文档

### 客户知识库

52. 作为客户用户，我想查看"客户知识库"（= 内部知识库 + 本项目文档），以便获得完整的操作指引
53. 作为客户用户，我想客户知识库**不包含其他客户**的任何文档，以便数据隔离

### 文档 → RAG 同步

54. 作为内部用户，我发布文档后 RAG 知识库自动同步（发布即同步），以便无需手动操作
55. 作为系统，文档发布与同步事件入队在同一事务（失败回滚），以便保证"已发布"必有同步尝试
56. 作为系统，同步失败自动重试（指数退避），以便容忍临时故障
57. 作为系统，同步按文档 scope 路由到正确 Index（内部文档→内部 Index，项目文档→客户 Index），以便隔离生效

### 内部客服 AI Agent

58. 作为内部用户，我想在独立"AI 客服"页面提问，以便基于全量知识库获得答案
59. 作为内部用户，我想答案带引用角标并可点击跳转知识库原文，以便核验答案来源
60. 作为内部用户，我想多轮连续对话（记住上下文），以便深入追问
61. 作为内部用户，我想回看/继续历史会话，以便复用之前的问答
62. 作为内部用户，我想通过悬浮小组件随时唤起客服 Agent，以便不离开当前页面
63. 作为内部用户，AI 客服可检索内部 KB + 所有客户 Index，以便提供跨客户支持（内部全权限）

### 客户操作手册自动生成

64. 作为内部用户（实施），我想选择蓝图版本 + 客户数据，手动触发操作手册生成，以便快速产出手册初稿
65. 作为内部用户，我想按章节分次生成、逐章审校/修改/单独重生成，以便保证质量
66. 作为内部用户，我想在审校完成后组装为一本完整手册，以便交付
67. 作为内部用户，我想生成结果自动存为项目知识库文档（草稿态、分类=操作手册），以便复用发布管线
68. 作为内部用户，我想把审校后的手册发布进客户知识库（RAG 自动同步），以便客户可检索
69. 作为内部用户，蓝图发布新版本时收到"建议重新生成"提示（不自动覆盖已审校内容），以便在合适时机更新手册
70. 作为内部用户，我想把优秀手册沉淀为内部标准操作手册，以便全平台复用
71. 作为客户用户，我想查看本项目自动生成的操作手册，以便获得基于真实数据的操作指引

### 权限与数据隔离

72. 作为客户用户，我想只能访问被授权项目的数据（任何 API 请求都受项目成员校验），以便隔离生效
73. 作为系统，数据库层 RLS 强制执行租户边界（即使应用层漏过滤也拒绝跨租户访问），以便红线兜底
74. 作为系统，RAG 检索由后端注入 Index 范围（API Key 仅存后端、绝不下发客户端），以便客户 B 无法触达客户 A 的知识
75. 作为系统，所有检索与数据访问行为写入审计日志，以便追溯
76. 作为内部用户，我想看到内部与所有客户的数据（内部全权限），以便履行支持职责

### AI 用量计量（Token 成本管理）

77. 作为系统，每次 LLM 调用自动记录 Token 用量（客户/项目归属、场景、模型、输入/输出 Token 数），以便 AI 成本可计量
78. 作为内部用户，我想按客户/项目/时间段/场景/模型查看 AI Token 用量统计与趋势，以便管理 AI 成本
79. 作为内部用户，我想让 Token 计量与 RAG 知识库成本（每客户 Index 规格费）联动，以便形成完整的客户 AI 成本视图

### 多模态与场景化多模型

80. 作为内部用户，我想为不同 AI 场景配置不同的 LLM 模型（客服问答 / 文档解析 / 手册生成 / Embedding 等），以便在质量与成本之间平衡
81. 作为内部用户，AI 功能支持多模态输入（如图片解析：draw.io 蓝图图、文档截图、附件图片），以便处理非纯文本内容
82. 作为系统，模型切换只改配置不改业务代码（场景 → 模型映射），以便无风险切换供应商

## Implementation Decisions

**技术栈（2026-08-04 定稿，全栈 TypeScript）**：前端 Next.js + React + TypeScript + shadcn/ui；后端 NestJS（Fastify 适配器）；ORM Drizzle（schema 内原生 `pgPolicy`/`pgRole` 管理 RLS）；Monorepo Turborepo + pnpm workspaces（`apps/web` + `apps/api` + `packages/shared` 类型 + `packages/contracts` zod 契约）；Agent 编排 LangGraph.js（开源核心 + PostgreSQL Checkpointer）；数据库标准 PostgreSQL（共享 schema + tenant_id + 客户级 RLS）；S3 兼容存储；消息队列可替换（RocketMQ 首选，事务消息）；Redis 会话/缓存；RAG 经 `DocumentIndexPort` 适配层（平台无关，候选 Dify/RagFlow/百炼）。

**LLM 抽象（`LLMClient`，升级为场景化多模型路由）**：
- 按**场景**（scene）路由：客服问答 / 文档解析 / 操作手册生成 / Embedding 等各自映射到配置的 provider + model（如 Qwen-Max 手册生成质量优先、Qwen-Plus 客服问答性价比、Qwen-VL 多模态图片解析）；**换模型 = 改配置，业务代码不动**
- **多模态支持**：`LLMClient` 支持文本 + 图片输入（draw.io 蓝图图、文档截图、附件图片的解析与理解）
- **AI 用量计量**：所有 LLM 调用统一经 `LLMClient` 记录用量（prompt/completion tokens、模型、场景、客户/项目归属、时间），落库 `ai_usage` 表；内部用户可按客户/项目/时间/场景/模型统计查看；与 RAG 每客户 Index 成本联动形成客户 AI 成本视图

**模块划分（NestJS 模块）**：

- **Auth & RBAC**：JWT + 租户域内角色权限；内部用户连接走旁路（`app.is_internal=true`），客户用户连接走 `SET LOCAL app.tenant_id`（每请求事务内设置，规避连接池会话变量泄漏）；**项目内邀请 = 创建客户账号的唯一入口**：新邮箱 → 待激活账号（占位密码不可登录）+ 客户归属 + 成员行 + 一次性邀请链接（7 天有效，`/invite?token=...`，由邀请者复制分发，**系统不发送邮件**）；客户点链接设密后激活（US-6）；成员列表分「真实成员」与「待激活邀请」两类；待激活邀请过期（7 天未激活）自动清理删除；重发邀请覆盖 token 使旧链接立即失效；取消邀请 = 直接删除该客户账号（链接随即失效）
- **项目管理**：客户 / 项目 / 蓝图（版本化：draw.io 文件入 S3 + 结构化内容入库，版本为一致性快照）/ 阶段 / 风险 / 会议纪要（富文本 + 附件）/ 问题清单（四态流转 + 评论 + 关联）；**项目边界在服务层校验**（访问控制中间件校验项目成员关系）
- **知识库**：文档 CRUD + 版本 + 分类 + Markdown 编辑 + 文件上传；发布/归档状态机
- **同步 Worker**：消费"文档变更"事件（事务消息），经 `DocumentIndexPort` 导入/轮询/幂等/删除；幂等键 = 平台文档 ID + 版本号
- **客服 Agent**：LangGraph.js 图（检索 / 生成 / 引用解析），检索范围后端注入，会话 checkpoint 持久化（PostgreSQL）
- **操作手册生成引擎**：蓝图解析（draw.io → 流程文本）+ 客户数据 → 分章节生成（`LLMClient`）→ 逐章审校 → 组装 → 存为项目知识库文档草稿

**API 契约**：`packages/contracts` 用 zod schema 定义前后端共享的请求/响应契约与校验。

**Drizzle RLS 模式**：业务表带 `tenant_id`，`pgPolicy`（`USING (tenant_id = current_setting('app.tenant_id', true))`）写在 schema 内随迁移管理；受限 DB 角色（非 owner、无 BYPASSRLS）连接。

## Testing Decisions

**接缝（seams）**：本仓库尚无代码，无既有接缝可用。建议以 **HTTP API 边界作为唯一最高接缝**——所有测试通过公开 API 验证外部行为（不测内部实现细节）；单元测试只覆盖纯逻辑（如状态机、蓝图解析），跨模块行为一律走 API 级测试。

**测试分层**：

- **单元测试**（Vitest）：纯逻辑——问题状态机、蓝图解析、幂等键计算；`LLMClient` 与 `DocumentIndexPort` 用内存 fake，测编排逻辑
- **契约测试**：`packages/contracts` zod schema 前后端共用，API 请求/响应必须通过契约校验
- **集成测试**（真实 PostgreSQL + RLS 策略）：服务 + 数据库全链路，重点验证 RLS 生效
- **隔离测试（红线）**：以客户 A 凭证访问客户 B 的资源 → 必须 404/403；跨客户检索测试（A 的检索仅命中 A 的 Index）——自动化渗透测试，上线门禁
- **同步 Worker 测试**：内存版 `DocumentIndexPort`，验证发布→导入→状态流转、失败重试、幂等

**Prior art**：无（新代码库）；测试模式参考 NestJS e2e（`supertest`）+ Drizzle 官方 RLS 示例。

## Out of Scope

- 第二阶段全部：会议视频信息提取、Monitor ERP 系统 API 集成、日历（甘特图）/邮箱同步、基于功能清单生成蓝图/风险清单、培训视频与学习平台、客户侧 AI Agent、其他内部 AI Agent
- 客户基础数据导入工具（用户明确暂不讨论，仅记录）
- 可配置权限/用户组/字段级权限（Phase 1 固定角色）
- Online help 文档的编写与交付（外部项目负责，平台仅提供导入通道）
- 视频生成（操作手册 → 视频）
- 问题解决后自动沉淀为 FAQ（待定，不在本期）
- 邮件发送（邀请/通知邮件）：邀请链接由邀请者复制分发，系统不发送邮件（US-4 修订决策）

## Further Notes

- **成本**：RAG 每客户一个 Index（约 21.6 元/库/月规格费），需设计休眠/归档策略；检索 TopK/Rerank 按需调参控 Token 成本；**AI Token 用量计量**（LLMClient 统一记录）与 RAG 规格费联动，形成客户级 AI 成本视图，为日后预算/告警/计费打基础
- **合规**：中国境内数据驻留；对外服务需 ICP 备案
- **上线门禁**：跨客户渗透测试通过后方可上线；审计日志留存
- **红线**：RAG API Key 只存后端；数据库 RLS 兜底；任何"已发布"文档必有同步尝试（事务消息）
- **风险**：NestJS + Drizzle 生态磨合（DrizzleModule 自封装）；LangGraph.js checkpoint 的 PostgreSQL 集成
